# Ozon: проверка состояния аналитического контура

Этот контур собирает каталог Ozon и выпускает обзор по всем товарам. Он не изменяет цены, акции, остатки или защиту на площадке и не вызывает Telegram. Сохранение отчётов в Git ограничено каталогом `data/ozon_profit_first_20261127/`; master остаётся источником только для чтения.

## Запуск

Workflow: `.github/workflows/ozon-profit-catalogue.yml`. Он запускает тесты перед чтением API; pull request запускает только тесты, без ключей Ozon. Расписание — раз в четыре часа, также доступен ручной запуск.

Локальное чтение при настроенных Ozon credentials:

```bash
python scripts/ozon_profit_snapshot.py --output data/ozon_profit_first_20261127/live --expected-count 147
```

Credentials берутся из существующего config; их не следует передавать аргументами или включать в отчёты. Для диагностики каждого запуска workflow создаёт отдельную папку runner. Старые отчёты из checkout не попадают в новый artifact при ошибке.

## Коды завершения и manifest

| Результат collector | Код | Что проверять |
| --- | ---: | --- |
| `complete_read_only` | 0 | Все секции собраны с заявленным покрытием. Это подтверждение сбора, а финансовая модель и решения о ценах требуют своей проверки. |
| `partial` | 2 | Прочитать `sections.*.status`, `coverage` и `errors`. Сохранён завершённый manifest. |
| `catalog_changed_review_required` | 2 | Сверить `catalog.active_count`, `expected_count` и точный список SKU/PID: каталог изменился относительно ожидаемых 147 товаров. |
| Fatal exception | 1 | Запуск не завершён штатно. Проверить безопасный код ошибки, наличие и состояние manifest; не принимать оставшиеся файлы за полный снимок. |

Workflow принимает код 2 для дальнейшей диагностики только при существующем, завершённом `READ_ONLY` manifest этого запуска с подходящим статусом и `seller_writes = 0`. Отсутствующий, незавершённый или несовместимый manifest останавливает job.

## Что блокирует свежий обзор

- Секции `products` и `prices` должны иметь `status = ok`, полный одинаковый набор точных SKU/PID и отсутствие ошибок идентичности. Пропуск страницы, дубликат, конфликт PID, неверная цена или неизвестный `archived` блокируют выдачу нового обзора. Старый снимок автоматически не подставляется.
- Неизвестная схема `protection` или неполная `finance` сохраняются как явные ограничения в обзоре остальных товаров. Число `min_price`, флаг автодобавления и действующая защита — отдельные сведения.
- `master.json` сохраняет `ozon_enabled` и `notes` из колонок `Ozon (да/нет)` и `Заметки`. Отсутствующий столбец, дублированный SKU или отсутствующий товар отмечаются в manifest. Ограничения владельца обрабатывает planner.

## Где смотреть результат

Artifact `ozon-profit-review-<run_id>-<attempt>` содержит только файлы текущего запуска: `live/manifest.json` и исходные секции, а после успешной классификации — `report/catalogue.json`, `report/summary.json`, `report/review.csv`. При отказе planner остаётся диагностический `live/`, новый catalogue не объявляется созданным. После успешной классификации workflow сохраняет отчёт и `live/` в изолированный каталог репозитория.

Финансы покрывают 30 полных календарных UTC-дней до вчера включительно. `finance.json` содержит агрегаты, `failed_dates`, несопоставленные SKU и нераспределённые начисления. Он не содержит `samples`, `debug_records` или сырых отправлений; временные диагностические записи существующего parser удаляются вне папки artifact. Ошибки parser и неизвестные распределения не следует трактовать как нулевые затраты.

Для проверки изменений без API:

```bash
python -m unittest discover -s tests -p 'test_ozon_profit_snapshot.py' -v
python -m unittest discover -s tests -p 'test_ozon_profit_catalog.py' -v
python -m unittest discover -s tests -p 'test_ozon_profit_economics.py' -v
```
