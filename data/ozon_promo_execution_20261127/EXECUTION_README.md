# Исполнение утверждённого пакета Ozon

Владелец утвердил точные 96 SKU, цены и action IDs из `approved_plan.json`. `experiment_floor_rub` равен утверждённой целевой цене и ограничивает эксперимент; он не объявляется рассчитанной полной границей прибыли. `scope_sha256` защищает неизменный состав решения. `enabled` — отдельный переключатель исполнения.

## Подготовка и применение

```bash
python scripts/ozon_promo_execute.py \
  --plan data/ozon_promo_execution_20261127/approved_plan.json \
  --snapshot data/ozon_promo_execution_20261127/evidence/live \
  --catalogue data/ozon_promo_execution_20261127/evidence/catalogue/catalogue.json \
  --contract data/ozon_promo_execution_20261127/official_contract.json \
  --service-evidence data/ozon_promo_execution_20261127/service_evidence.json \
  --journal data/ozon_promo_execution_20261127/execution_journal.json \
  --report data/ozon_promo_execution_20261127/execution_report.json
```

Без `--execute` команда только готовит точные запросы и локальный отчёт. Для применения добавляется `--execute`; persisted plan должен иметь `approved=true, enabled=true`. Снимок и построенный из него catalogue должны быть свежими: максимум 15 минут для обязательных секций. Каждая разрешённая запись дополнительно проходит live-проверку и одноразовый permit `ozon_control_guard`.

Порядок на SKU: прочитать цену, наличие и все акции; проверить фактические тарифы и финансовые ограничения; продлить защиту и подтвердить active/expiry; установить точные price/min_price с сохранением old_price; добавить только разрешённые активные акции; проверить фактические цену, минимум, защиту, участие и бустинг. Для группы A сохраняются прежние активные участия и бустинг. Исходные и итоговые `website_prices` остаются в отчёте.

Если timer/update не активировал отключённую защиту, цена этого товара ещё не меняется. Неизвестные auto/protection flags не подбираются запросами. Для future-only записей используется `DEFERRED_FUTURE_ONLY`, без раннего снижения цены и без выдачи планирования за активное участие. Следующий запуск после старта использует первоначально утверждённую цену, а не новый процент от последнего результата.

## Журнал и проверка

Перед mutation на диск атомарно сохраняется `INTENT`. Запрос выполняется один раз; сетевые ошибки и неполные ответы проверяются чтением. Незавершённая операция блокирует новые записи данного SKU до readback. Повторный запуск не переписывает уже применённую цену, если продавец позднее изменил её вручную, в том числе вернул к первоначальной. Автоматического отката других товаров нет.

После каждого чтения сохраняется фактический `last_verified` в плане. Пока эффект mutation не подтверждён, запись помечена `verified=false`: legacy-процессам нельзя восстанавливать старую коммерческую цену из прежнего снимка. Успешный readback публикуется до следующей mutation. Полный рассчитанный profit во всех этих состояниях остаётся неподтверждённым; неизвестные расходы сохраняются как неизвестные.

`official_contract.json` — минимальные ограничения запроса по указанным первичным источникам и наблюдениям API, с честной квалификацией составного доказательства для нового action update. Это не скачанная полная OpenAPI. Future enrollment schema не объявлена проверенной и не отправляется. Ошибки сервера хранятся без тела ответа, credentials и сырых текстов исключений.

Коды завершения: `0` — подготовка/исполнение без HOLD (отложенные будущие акции допустимы); `2` — есть изолированные HOLD, смотреть отчёт; `1` — общая ошибка конфигурации или обязательных исходных данных. Для возобновления используется тот же journal, а не новый пустой файл.
