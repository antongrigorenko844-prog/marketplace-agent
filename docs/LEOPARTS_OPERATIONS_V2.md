# LEOPARTS — операции v2 (23 ноября 2026)

## Назначение
Быстрая замена **одной утверждённой обложки** без полной синхронизации каталога и **читаемые статусы по площадкам**. Отдельный безопасный аудит старых заказов, отдельная подготовка Tilda и Авито. Никакие новые операции не должны изменять цены, остатки или состав комплектов.

**Главная команда:** [Actions — LEOPARTS Operations v2](https://github.com/antongrigorenko844-prog/marketplace-agent/actions/workflows/leoparts-operations-v2.yml)

| Операция | Что делает | Запись в кабинеты | Когда использовать |
|---|---|---|---|
| status | Публикует единый отчёт о проверках | Нет | Любое время |
| media / inspect | Проверяет обложку Ozon, WB, Яндекс Маркет по SKU | Нет | Перед заменой |
| media / apply | Меняет ТОЛЬКО первое фото указанного SKU на выбранных площадках | Только фото, по явному согласию | Когда утверждённая картинка уже в `data/content_manifest.json` |
| stock | Сверяет текущие Ozon FBS/FBO с журналом | Нет | При сбое учёта заказов |
| avito / inspect | Сравнивает фид с утверждённым фото | Нет | До восстановления автозагрузки |
| avito / apply | Обновляет одну ячейку Photo в стабильном XLSX-фиде | GitHub Release, только после подтверждения тарифа | После оплаты Авито |
| tilda / inspect | Создаёт CSV с `TildaUID;SKU;Photo` и проверяет первую картинку | Нет | Для точечной замены в каталоге Тильды |

### Как читать результат
- `verified` — целевое изображение подтверждено по данным площадки/изображению.
- `pending_platform` — API принял изменение, но не подтверждено на витрине.
- `feed_published_listing_unverified` — новый фид существует, но НЕ значит, что Авито уже изменил объявление.
- `manual_csv_import_needed` — CSV готов, но в Tilda ещё не импортирован.
- `not_applied` — предварительная проверка без публикации.
- `failed` — ошибка или невозможность проверить.

Файлы: `data/leoparts_ops_status.md`, `data/leoparts_ops_status.json`. Каждый канал имеет отдельный статус, отказ одного не превращает успешные изменения другого в ошибочные.

### Утверждение нового фото
1. Проверить артикул, поколение и комплектацию по **реальному** фото.
2. Разместить файл на стабильном публичном HTTPS.
3. Зафиксировать URL в `data/content_manifest.json` только для точного SKU (фотографии Ozon/WB/Market и Авито могут отличаться).
4. Запустить `media / inspect`, затем `media / apply` с явной отметкой.
5. Проверить статусы. Если `pending`, повторить `media / inspect` позже.

Программа не изменяет цены/остатки и не вызывает команды полной синхронизации. Авито отделён от этих действий; задержка его тарифа не должна задерживать фото на остальных площадках.

### Tilda
Старый CommerceML **добавлял** картинки, а не менял первую. Повторная отправка CommerceML с целью заменить главную картинку запрещена, пока не подтверждён API, который действительно заменяет фото.

Файл `data/tilda_cover_patch.csv` содержит только `TildaUID`, `SKU` и `Photo`. В каталоге Tilda: **⋯ → Импортировать (или обновить) товары из CSV → сопоставить поля → включить «Обновить только существующие товары и не создавать новые» → проверить первое фото на опубликованном сайте**. Экспортировать текущий CSV до импорта — резервная копия.

Документация Tilda: https://help-ru.tilda.cc/online-store/import-export

### Заказы и остатки — отдельная высокоприоритетная проблема
Исторические записи Ozon FBS/FBO, WB и Маркета содержат списания без сохранённой на момент продажи спецификации компонентов. При отмене/коррекции такого заказа штатный `stock_transaction.OrderBatch.reconcile` прекращает расчёт, не угадывая состав; это защитный механизм, а не ошибка, которую можно «исправить» отключением проверки.

`stock_preflight.py --live` **только читает** текущие заказы и SQLite в режиме read-only. Он выводит обезличенный хеш заказа, SKU, количество и причину блокировки. Для исправления каждой реально конфликтующей строки требуются подтверждённые исторические данные о компонентах и движении склада; переносить текущую BOM-схему на старые заказы нельзя. Код восстановления списаний и цены здесь не запускаются.

Важная граница: отсутствие конфликтов за 30 дней **не доказывает**, что все исторические остатки верны. При необходимости — отдельная сверка с физическими остатками.

### Тесты
- `tests/test_media_fast.py`: только фото, точный SKU, независимые каналы, WB проверка пикселей.
- `tests/test_stock_preflight.py`: old-order no-op, блокировка несовпадений и отрицательных/неизвестных входов.
- `tests/test_avito_fast_cover.py`: не менять соседние ячейки, стоимость и остатки, не публиковать при неоплаченном тарифе.
- `tests/test_tilda_cover_csv.py`: точный TildaUID и CSV только с фото.
- `tests/test_ops_status.py`: не выдавать отправленный фид за опубликованный товар.

### Упорядочивание
Исторические разовые workflow и скрипты сохраняются в истории Git и/или папке `.github/workflows-archive/`, но не должны быть активным интерфейсом для следующих правок. Служебные регулярные складские/рекламные задания нельзя массово удалять или перезапускать без проверки ссылок и зависимостей. Новые типовые изменения делаем через одну Operations v2, а не новый workflow на каждый артикул.
